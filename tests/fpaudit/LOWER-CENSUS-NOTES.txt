Q pipeline -- RESOLVED (this commit):
  The "lane-selection anomaly" was a rig readback artifact: the
  recompiler retires committed Q into VI[REG_Q] (microVU_Branch
  block-end flush), not the q field the readback compared, so the
  Q column was seed-vs-computed. The lane-identified probe (distinct
  exponent per lane, 16 fsf/ftf combos) then showed 16/16 bit-exact
  agreement -- no decode disagreement exists. The exec export now
  mirrors the recompiler's committed VI[REG_Q]/VI[REG_P] into the
  q/p fields so the readback slots are engine-agnostic.

  Real Q census (400 cases): default DIV 183, SQRT 106, RSQRT 184
  divergent -- one-ulp chop-vs-model plus overflow clamp-vs-saturate,
  the classes exact divide exists for; wire proven live (183/400
  def-vs-exactdiv rec deltas). Under exactdiv: DIV 0, SQRT 0,
  RSQRT 7 -- and the RSQRT residual was an ORACLE bug: every case
  was ft = -0, where the interpreter's hand-coded zero-denominator
  path XORed both signs while the hardware-verified model, the
  exact stub, and the recompiler's default emission all agree the
  sqrt stage strips the denominator sign (saturation by numerator
  sign alone). With the interpreter corrected: DIV 0, SQRT 0,
  RSQRT 0 -- the exact-divide option is bit-exact for the entire
  Q pipeline, its first accuracy verification.

Rig lessons banked this battery:
  - The q field sits at regs_io offset 656 (after the 16-byte ACC at
    640); the first analysis read 644 -- inside ACC -- and produced
    an all-zero Q column that the executed-effect check (q_out must
    differ from q_in) exposed. That check is now part of the
    standard battery integrity set alongside files-must-differ and
    known-answer splits.

SUB/ADD asymmetry -- CLOSED (follow-up to the elide commit): the
anatomy peek showed every divergent SUB lane carrying a raw exp-255
operand, the oracle arithmetically correct by inspection, and the
recompiler's results all clamp signatures (several with the wrong
sign). The source is mundane: mVU_SUB carries Kingdom Hearts-era
input clamp flags (cFs|cFt) that mVU_ADD does not, and those clamps
flattened exp-255 operands before the accurate composite's detector
could route them -- ADD's exactness on the same distribution
through the same composite is the proof raw operands are handled.
The fix extends the exactmul elide: under the accurate add/sub
option, add/sub input clamps are elided. SUB: 205/400 to 0/400; ADD
and MUL hold at zero; default rig outputs byte-identical; 300
frames of Tekken under the option pixel-identical. MADD/MSUB
(115-122/400) remain open -- their clamps live in the fused FMAC
bodies and get the same per-site treatment next session.

Fused front, the decomposition probe -- mechanism NAILED, design
work scoped (no code shipped this session; a candidate cACC-clamp
elide measured as a no-op in every tested context and was reverted
per the standing rule):
- Decomposed MUL-then-ADD over the identical operands and dataflow:
  0/400 -- the standalone composites are exact on everything the
  fused ops see, saturated products included.
- Fused MADD on the same cases: 158/400. And the decisive third
  number: the decomposed ORACLE disagrees with the fused ORACLE on
  exactly those 158 cases. The interpreter's MADD is not
  mul-then-add: the hardware model's fused datapath hands the adder
  the pre-saturation wide product (exponent above 255 preserved
  into the add), where the recompiler's fused path -- and any
  decomposition -- adds the saturated float. On saturating products
  the two semantics differ, and the recompiler currently implements
  decomposition semantics.
- The closing work is therefore a design item with an exact spec:
  the fused composite's mul stage must hand its add stage the
  pre-saturation exponent/mantissa (the exact stage already
  computes wide intermediates internally; the hand-off must bypass
  the float-format saturation between stages). Verification target:
  fused rows to 0/400 on the adversarial distribution, plain rows
  held at zero, default byte-identical, pixels identical.
- Prerequisite before any emission work, per rule 10: confirm the
  oracle's fused-vs-decomposed split against hardware expectations
  (the ps2f suite's MADD lineage), since this is now the load-
  bearing semantic claim. One hardware capture -- FMAX*FMAX MADD
  -FMAX on silicon -- settles it alongside the queued CFC1 and EFU
  items.

Fused MAC overflow rule -- IMPLEMENTED AND CLOSED (this commit):
the model's own source supplied the exact semantics ahead of the
hardware capture (ps2f_mac_finish: mul-stage overflow forces the
sign-selected all-ones saturation pattern regardless of the add;
MADD's pattern sign follows the product, MSUB's is flipped), which
derisks proceeding since the model is the hardware-verified suite's
encoding; the silicon capture stays queued as confirmation. The
emission is a per-lane detect-and-blend around the fused add,

first, broader exponent-field detector wrongly captured exp-255
products with computed mantissas, which come from exp-255 INPUTS,
carry no overflow in the model, and flow into the add normally
(residual 3-5/400 with that detector, anatomy on record). With the
pattern detector: MADD 115-to-0, MSUB 122-to-0 on the adversarial
distribution, the decomposition probe's MADD row also zero, plain
rows held at zero, default rig outputs byte-identical, 300 frames
under both options pixel-identical. FMACb (MADDA/MSUBA) is not yet
wired -- same helper, its ACC dual-path insert next session, with
MADDA/MSUBA rows added to the adversarial battery. Flag-side OF
forcing for blended lanes is ledgered with the flag residuals, not
silently claimed.
